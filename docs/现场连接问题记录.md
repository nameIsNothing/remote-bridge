# 现场连接问题记录

> 本文记录实际使用 Remote Bridge 连接目标机时遇到的问题、临时解法与根因，供后续在程序里消化。按时间倒序追加。

## 2026-10-28 · 管理端经 SSH 隧道连 DESKTOP-AVEMMJD

- 管理端：WIN-3U6O21LUQN9（开发机经反向 SSH 隧道登入，非交互会话）。
- 目标机：DESKTOP-AVEMMJD，`192.168.100.67`（WiFi），当前账号 `DESKTOP-AVEMMJD\1`，WinRM 当前账号直连模式。

### 问题一：管理端发现不到目标（UDP 广播）

- 现象：`bridge-cli` 默认流程报「未发现正在等待连接的电脑」。目标广播正常开着。
- 根因：管理端是多网卡机器（除真实局域网 `192.168.100.0/24` 外，还有 VMware `192.168.7.1`/`192.168.140.1`、WSL `172.24.144.1`）。`internal/discovery/discovery.go` 的 `Discover` 只在单个 socket 上向单一广播地址 `WriteToUDP` 一次；默认 `255.255.255.255`（受限广播）在多网卡机器上只从操作系统选中的一块网卡发出，没落到真实网段，目标收不到。
- 临时解法：显式指定定向广播地址，`-broadcast 192.168.100.255`。三个连接子命令（`ssh`/`manage`/`connect`）和 `discover` 都支持。
  - 实测：`255.255.255.255` 发现 0 台；`192.168.100.255` 发现 1 台。
- 建议根治：发现时枚举本机所有 IPv4 网卡、按各自子网算出定向广播地址逐个发送，覆盖全部网段，不再依赖单一 `255.255.255.255`。改动集中在 discovery 发送路径，需补对应测试。

### 问题二：连接时「拒绝访问」（WinRM 授权）

- 现象：发现成功、输入密码后，`[authentication] 连接到远程服务器 192.168.100.67 失败 … 拒绝访问`。5985 端口可达，防火墙没挡，卡在认证授权。
- 根因：当前账号直连模式（`--current-user`）的 apply 只做「WinRM 服务 + 监听器 + 仅本网段防火墙规则 + 校验当前账号身份」，**不授予任何 WinRM 权限**（见 `internal/platform/windows/plan.go`：`apply.account-group`「加入 Remote Management Users」只在临时账号分支里做，当前账号分支跳过）。这与安全边界一致（当前账号模式「不创建或修改账号、不自行扩权」）。于是要求当前账号本身已有 WinRM 远程权限，否则被拒：
  - 账号是非内置管理员 → UAC 远程令牌过滤，网络登录拿到降权令牌，不在 WinRM 默认 SDDL（Administrators 全令牌 / Remote Management Users）内 → 拒绝。
  - 账号是标准用户 → 不在上述两组 → 拒绝。
- 临时解法（在目标机手动授权，二选一）：
  - 管理员账号：`reg add "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System" /v LocalAccountTokenFilterPolicy /t REG_DWORD /d 1 /f`（机器级，免重启，持久）。
  - 标准/任意账号：`net localgroup "Remote Management Users" <账号> /add`（更小权限、可回收；找不到组名用 SID `*S-1-5-32-580`）。
- 说明：`bridge-target inspect` 当前账号模式只校验身份是否匹配，不检查 WinRM 授权，所以事先发现不了这个问题。

### 待评估：能否在目标机「打开程序」时处理授权这步

结论：**应当增加“检测 + 清楚告知”，但“自动扩权”要慎重，需显式单独同意且可回收。**

- 应做：当前账号模式开窗时，检测当前账号是否真的能用于 WinRM（是否内置 Administrator、是否在 Remote Management Users、非内置管理员时 `LocalAccountTokenFilterPolicy` 是否为 1）。不满足就在检查清单里以「异常」明确提示原因与修法，而不是让管理端撞到含糊的「拒绝访问」。这与工具「检查并说明」的定位一致，低风险。
- 慎做：`LocalAccountTokenFilterPolicy=1` 是机器级、对所有本地管理员生效且持久的 UAC 削弱，属安全边界明确禁止的「自行扩权/未授权持久化」。若提供，必须是单独、显著标注、可回收的显式选项（revoke 要能还原）。
- 相对可接受：把账号加入 Remote Management Users（临时账号路径本就这么做，范围更小、可随 revoke 删除）。但当前账号模式动的是用户“真账号”的组成员身份，比临时账号更具侵入性，同样要显式同意 + 结束时清理。
- 另一思路：当检测到当前账号不具备 WinRM 权限时，引导改用「临时账号模式」——该模式已自建 `RemoteBridge` 账号、自动加入 Remote Management Users，并在 revoke 时清理，天然规避本问题。
